# ADR-021: Human identities and revocable browser sessions

Status: accepted for the local Phase 15 human-session checkpoint, 2026-09-26.
Local database role grants are separately verified in ADR-023. Actual remote
deployment verification remains open.

## Context

The Phase 14 browser holds an operator-pasted service credential in memory. Human
accounts need password verification, current roles/scopes and centrally revocable
sessions. The domain must remain framework-free. Existing machine credentials,
immutable actor UUIDs and authorization-before-idempotency semantics must survive.

## Decision

Use PostgreSQL-backed opaque sessions rather than JWTs. Every authenticated request
must check the current account and session; a JWT would still require a database
lookup for immediate revocation and scope changes. No signing key or JWT claim cache
is needed. Human accounts have one analyst or admin role; never the service role.
Account UUIDs are generated by trusted provisioning, never supplied by a browser or
recycled. Provisioning must reject collisions with configured service principal IDs.

Passwords use Argon2id with explicit RFC 9106 low-memory parameters (64 MiB, three
iterations, four lanes, 16-byte salt, 32-byte output). Passwords accept 15–128 Unicode
characters, at most 512 UTF-8 bytes, without trimming or normalization. No complexity
rules or routine forced expiry. Accept pasted passwords/password managers. Reject
surrogates and check length before hashing. Deployment must measure memory/latency
and set concurrency limits before remote use; library defaults are not policy.

Use random 256-bit access, refresh and CSRF values. Store token SHA-256 digests only.
Access expires after five minutes. Refresh expires after 30 idle minutes and each
family expires absolutely after eight hours. Rotation replaces access/refresh/CSRF
values, retains consumed refresh digests until family expiry and never extends the
absolute deadline. Reusing a consumed refresh token revokes the whole family,
including its newest access token. Concurrent refreshes serialize; the second is
reuse and forces login. No grace window. The browser must serialize refresh in a
tab; competing tabs may require reauthentication. Unknown tokens never revoke an
unrelated family. A consumed token may be recognized only after valid CSRF/origin
checks, avoiding unauthenticated logout attacks.

Every account/password/role/scope/active-state change increments an authorization
version and revokes all sessions atomically. Reads resolve current account policy.
Already authorized in-flight work may finish; revocation governs subsequent
authentication, not cancellation of a transaction already executing. Reviewers and
learning authorizers remain distinct UUIDs; no role or UI flow bypasses learning.

## Browser and HTTP contract

- POST `/api/v1/auth/login`, `/refresh`, `/logout`; GET `/session`.
- Access/refresh cookies: host-only, HttpOnly, SameSite=Strict, Path=/, Secure by
  default. Use `__Host-` names with TLS. Explicit localhost development mode may
  use unprefixed non-Secure cookies; production must reject this mode.
- Every cookie-authenticated unsafe request requires exact configured Origin and a
  constant-time checked `X-CSRF-Token` bound to the session generation. Login also
  requires exact Origin and JSON content type. Missing/null/foreign origins fail.
- GET session returns account UUID, role/scopes and current CSRF value with no-store;
  never return access/refresh tokens or password hashes. CSRF is not an auth token.
  A third HttpOnly cookie carries the random CSRF value under the same cookie rules;
  the server validates it against the generation's digest before returning it.
  This permits reload without storing plaintext CSRF in PostgreSQL. Consumed refresh
  records retain the corresponding CSRF digest for authenticated reuse detection.
  If access has expired but a current refresh cookie remains, GET session returns only
  the validated CSRF and `refresh_required=true`; the browser must then rotate before
  requesting business data.
- Reject mixed bearer/cookie credentials. An invalid Authorization header must never
  fall back to a cookie. Machine bearer requests retain existing authorization.
- Do not enable CORS for arbitrary origins; do not derive trust from Host,
  X-Forwarded-Host or forwarded client IP supplied by a caller. Configure explicit
  origin, hosts and trusted proxy addresses. Production requires verified TLS.
- Logout revokes the family and clears all cookies with matching attributes.
  The frontend must clear retained customer data when authentication expires.

## Persistence, provisioning and abuse controls

Add accounts, session families/generations and shared login-limit state through an
additive migration. Account and family locks serialize changes and rotation. A
single explicit commit records state changes and immutable audit entries; failures
must roll back. Do not emit unsupported auth events into the existing outbox.
Existing business audit/outbox/idempotency transactions remain intact.

Provisioning/recovery initially uses a local operator CLI, with getpass for secrets,
no password command-line arguments and no public registration/reset endpoint.
Operator actions require an explicit non-secret actor identity and audit trail.
Recovery resets the password and revokes all sessions after out-of-band identity
verification; this project cannot claim that a local CLI verifies a person's identity.

Use shared PostgreSQL counters and atomic reservations before expensive hashing:
256 hashed identifier buckets plus an overall login budget, with bounded windows and generic
failure responses. Unknown users use a fixed dummy Argon2id verification. Return
the same failure for unknown, inactive, expired, locked or incorrect accounts.
No permanent lockout and no automatic reset token emailed by this application.
Rate-limit state must survive processes/restarts and remain bounded. A reverse
proxy must separately bound connection time, bodies and expensive-request concurrency.

The implemented local policy allows ten attempts per hashed identifier bucket and
100 attempts overall per minute. Buckets can collide and therefore conservatively
throttle unrelated logins. This is an authored safeguard, not a measured operating
point. Consumed refresh digests remain immutable until the eight-hour family expiry;
up to 100 expired rows are pruned during each login. The database rejects early deletion.
The browser keeps CSRF only in tab memory and serializes refresh requests in that tab.

Runtime database grants, TLS/proxy verification, edge limits, MFA and operator recovery
assurance are not supplied by this local implementation. The CLI accepts an asserted
operator UUID; actual operator identity must be controlled by the local OS procedure.

## Alternatives and consequences

Rejected: browser localStorage tokens; reusable long-lived refresh without detection;
stateless roles in JWTs; process-local throttle counters; automatic service-to-human
identity conversion; public self-registration; and unaudited database password edits.

Server-side lookup adds a database dependency to human authentication. Strict refresh
reuse handling can log out legitimate concurrent tabs. These tradeoffs favor explicit
revocation and auditability in a small modular monolith. MFA, managed identity and
high-assurance recovery remain requirements to evaluate before remote exposure.
